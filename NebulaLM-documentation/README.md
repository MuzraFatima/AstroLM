# NebulaLM

NebulaLM is a decoder-only transformer language model trained from random initialization on a curated, licensed corpus of space and astronomy text. Version 1 targets approximately 29 million parameters, a 256-token context window, and training on one local RTX 3050-class GPU.

NebulaLM is a base language model and an educational/research portfolio project. It is not a chat assistant, factual reference, or substitute for verified astronomy sources.

## Project objective

The project has two coupled objectives:

1. Engineer and verify a complete language-model pipeline: provenance-aware data collection, deterministic preprocessing, a train-only byte-level BPE tokenizer, a hand-implemented GPT-style model, resumable mixed-precision training, and reproducible evaluation.
2. Answer the following falsifiable research question:

> Under the same curated training corpus, tokenizer, context length, and measured training-token budget, does the approximately 29M-parameter NebulaLM configuration achieve lower held-out astronomy bits-per-byte than both a 5-gram language model and an approximately 10M-parameter transformer baseline, without pervasive verbatim memorization?

The final report must answer this question even if the answer is no.

## Fixed scope

- Domain: space and astronomy
- Objective: causal next-token prediction
- Model family: decoder-only, pre-norm transformer
- Training: from random initialization; no pretrained weights
- Compute: one local GPU; no distributed or cloud requirement
- Interface: sampling script only
- Out of scope: instruction tuning, chat behavior, RAG, frontend work, distributed training, and factual-authority claims

## Planned default configuration

The planned 8k-token configuration uses 8 layers, 8 attention heads, a 512-dimensional embedding, and a 256-token context. The exact parameter count must be generated by code from the frozen tokenizer and resolved run configuration. A vocabulary change changes the parameter count, so “29M” is a target label rather than a constant independent of configuration.

Runtime YAML configuration files, once implemented, are the executable source of truth. Markdown documents describe constraints and procedures but must not duplicate unresolved run values as if measured.

## Evidence required before claiming success

- Dataset manifest, license audit, cutoff, split hashes, and quality report
- Tokenizer comparison and round-trip tests
- Model correctness tests and exact save/resume test
- Measured VRAM, throughput, and wall-clock estimate
- Frozen validation and test protocols
- 5-gram and smaller-transformer baselines
- Per-source test loss, controlled generations, factuality/cloze results, and memorization analysis
- Complete experiment log including failed runs

No estimated corpus size, runtime, loss, factual accuracy, or qualitative result may be presented as achieved until it has been measured and recorded.

## Workstreams

The work is organized into three assignable workstreams:

| Workstream | Owns | Publishes interfaces used by others |
|---|---|---|
| Data / Dataset Pipeline | collection, provenance, licensing, cleaning, deduplication, splits, shards | manifests, schemas, frozen split IDs, corpus report |
| Model / Tokenizer / Training | tokenizer candidates, model, optimizer, trainer, checkpointing, sampling | tokenizer bundle, configs, checkpoints, training logs |
| Evaluation / Experiments / Reproducibility | evaluation sets, baselines, run registry, verification, reporting | evaluation bundle, test runner, experiment records, final report |

Workstream boundaries indicate ownership, not isolation. Changes to a published interface require review from every consuming workstream.
